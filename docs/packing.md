# DAZZLE.EXE PKLITE packaging

## Result

**Status: partial; no exact pack has been proved.** The original packed MZ word at `0x1c` is `0x310c`: PKLITE 1.12 with the `-e` extra-compression bit and the large-codebook bit. The target MZ is 80,641 bytes (`SHA-256 46e3699558773b23e91a86ada46164f5909fed966e819d2ec9eb96dc487aed57`). The `-e` option is explicitly marked commercial-only in the acquired shareware utilities, so the required executable is PKLITE 1.12 Professional.

The 1.12 Professional executable was not obtained. Internet Archive advanced searches for `pkltp112.rar` and the exact “PKLite 1.12 Professional” title returned no direct file record. A VETUSWARE listing identifies `pkltp112.rar` (36.6 KB; listed CRC32 `CB2E09F6`), but its download host did not resolve during acquisition, and no SHA-256 could be recorded. The 1.12 shareware utility rejects `-e` with exit code 1 and creates no output. The archive listing and the shareware help output agree that Professional is required. See the [VETUSWARE listing](https://vetusware.com/download/PKLite%201.12%20Professional/?id=9763).

Independent format analysis describes `0x10` as the `-e` flag and `0x20` as the large variant; the same notes list the 1.12–1.15 release dates and versions. The PKLITE utility itself confirms the dates, options and `-e` restriction in its DOS help screen. [PKLITE format notes](https://entropymine.wordpress.com/2021/12/19/notes-on-pklite-format-part-1/)

The control input was `reference/DAZZLE_U.EXE` truncated at its MZ extent, 211,302 bytes (`SHA-256 4761aea4c39407a27c4e961ce63dc75e69e0d3df2f3156b7b8d009b4d366d558`). Every shareware result is 42 bytes too large. At the first mismatch, offset `0x02`, the target has `e_cblp=0x0101`; each control output has `0x012b`. The target version word is `0x310c`; the controls report `0x210c`, `0x210d`, `0x210e`, and `0x210f` respectively. These are negative results, not matches.

For this overlay-free input, default, `-a`, and `-n` produce identical bytes for each release. `-b` creates `BTEST.BAK` containing the original input; the packed `BTEST.EXE` is byte-identical to the 1.12 default result. Therefore `-a` versus default cannot be inferred from this input, and `-b` is a backup behavior rather than a compression mode.

Additional 1.12 shareware input-header sweeps varied minalloc, maxalloc, checksum, overlay number, one extra header paragraph, and relocation order. The outputs remained 80,683 bytes. The default decoded relocation order is the strongest current hypothesis; sorting or reversing it changed bytes in the compressed relocation stream at approximately `0x1280e` and `0x12803`. The candidate host header changes with source header settings. The target stores no ordinary copied pre-pack header under `-e`, so its original checksum, overlay number, maxalloc and TLINK relocation ordering remain unproved.

The MZ header generated by `tools/unpack_pklite.py` carries `minalloc=0x1ff6` from the packed host header. That is not a recovered original value. With shareware 1.12, packing this input yields host `minalloc=0x3d7b` and startup `AX=0x511b`; lowering the input minalloc to 0–626 yields host `minalloc=0x1ff7` and `AX=0x3397`. The target has host `minalloc=0x1ff6` and `AX=0x3395`. These one- and two-paragraph differences are consistent with a different `-e` stub/relocation payload, but do not identify the original TLINK header. Empirical v1.12 allocation formulas also show that host allocation fields depend on the original header and compressed relocation size. [v1.12 allocation analysis, part 2](https://entropymine.wordpress.com/2026/04/24/pklite-supplement-7-min-max-alloc-part-2/)

## Input header and relocation hypotheses

The current reconstructed input MZ has `e_cparhdr=610`, `e_minalloc=0x1ff6`, `e_maxalloc=0xffff`, checksum zero, overlay zero, and the decoder's ordered relocation list. The 610-paragraph header is the minimum size needed for 2,431 relocation entries at `e_lfarlc=0x1c`. Stack and entry registers are recovered from the decoder footer. The exact pre-pack min/max allocation, checksum, overlay and relocation order are not encoded in the target `-e` output.

The app's appended resource is a separate step. `tools/pack.py` obtains the 78,251-byte tail directly from the original distribution after validating the immutable full-file and tail hashes, appends it after the candidate packed MZ, and writes an output only after a strict full-file equality check. This is explicitly **“appended resource from original distribution”**; the ten-byte frame and LZH stream are not regenerated.

Once the real 1.12 Pro binary and a justified pre-pack header are available, run:

```powershell
python -I tools/pack.py reference/DAZZLE_U.EXE build/DAZZLE.EXE --pklite C:\tools\pklite-1.12-pro\PKLITE.EXE
```

The script validates the input relocation-site multiset against `evidence/oracle.json`, keeps the input order as supplied, then invokes `PKLITE.EXE -e -a DAZZLE.EXE PACKED.EXE` under MS-DOS Player. It checks the `0x310c` variant and compares the entire packed MZ before it appends the tail. A mismatch reports the first byte and leaves the requested output unwritten. Current shareware 1.12 intentionally fails at `-e`; no full-file `EXACT` claim has been made.
